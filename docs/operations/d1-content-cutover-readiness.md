# D1 content cutover readiness

This checklist is the final safety gate before removing the bundled TOML fallback from the public portfolio loaders.

## Safety boundary

- Do not remove `src/lib/data/*.toml` or the fallback paths until the checks below pass in the intended Cloudflare D1 database.
- `wrangler.toml` currently documents the D1 database as shared by Preview and Production. Treat remote writes as production-impacting.
- This runbook contains read-only SQL. It does not apply migrations, seed content, or modify D1.
- Exporters are the source-to-SQL step; review generated SQL before any approved remote import.

## 1. Confirm migration history

From a trusted local checkout, inspect the configured database and migration status:

```sh
pnpm d1:migrations:list
```

Confirm the content schema migrations and the projects schema migration are applied. The project seed is generated by `pnpm d1:export-projects`; do not assume it has been applied merely because `0003_projects.sql` is present.

## 2. Check portfolio content (read-only)

Run these queries in the Cloudflare D1 console for the intended database.

Expected core content: exactly six rows, one each for `cv`, `site`, and `skill_stories` in both `es` and `en`.

```sql
SELECT locale, content_key, COUNT(*) AS rows
FROM portfolio_content
GROUP BY locale, content_key
ORDER BY locale, content_key;
```

The result must contain all six locale/key combinations with count 1.

Check payload validity:

```sql
SELECT locale, content_key
FROM portfolio_content
WHERE json_valid(payload_json) = 0;
```

Expected: no rows.

## 3. Check CV document records

```sql
SELECT locale, document_key, public_path, is_current
FROM portfolio_cv_documents
ORDER BY locale, sort_order, document_key;
```

Confirm the current document records and public PDF paths match the intended CV documents, and that the Spanish records are present. Confirm any required English records have been intentionally handled; the current exporter seeds the four CV records under `es`.

## 4. Check project content (read-only)

```sql
SELECT
  COUNT(*) AS total_projects,
  SUM(CASE WHEN is_published = 1 THEN 1 ELSE 0 END) AS published_projects,
  SUM(CASE WHEN json_valid(content_es) = 0 THEN 1 ELSE 0 END) AS invalid_es,
  SUM(CASE WHEN json_valid(content_en) = 0 THEN 1 ELSE 0 END) AS invalid_en
FROM portfolio_projects;
```

Expected: total and published counts match the reviewed project export; both invalid JSON counts are 0.

Check bilingual slugs and publication state:

```sql
SELECT slug, is_published, sort_order
FROM portfolio_projects
ORDER BY sort_order, slug;
```

Compare the slug set and localized payloads with the generated `migrations/0004_projects_seed.sql` and the current source project TOML. Do not mark this gate complete based on row count alone.

## 5. Runtime verification after a deployment

- Open `/proyectos` and verify public projects match the approved D1 data.
- Open at least one published and one unpublished project detail URL; unpublished content must not be publicly exposed.
- Open `/cv`, `/habilidades`, and `/sitemap.xml`; verify the current D1 content is reflected.
- Verify `/sitemap.xml` contains only published project URLs, valid XML, and no duplicates.
- Confirm server logs do not report D1 fallback warnings.

## Cutover decision

Only after the database checks and runtime checks are documented as passing should a separate PR remove TOML imports and fallback code. Keep the cutover in its own reviewable PR. Do not delete source TOML in the same operation as an unverified remote seed.
